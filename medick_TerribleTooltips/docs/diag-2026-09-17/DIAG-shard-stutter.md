# Affix Shard hover stutter — diagnosis only

Date: 2026-09-17. Seat: ASTRA, builder; no independent approval claimed.
Target: Trunks1981's 2026-09-12 report against Terrible Tooltips 3.0.2 (FPS as low as 17), with FallenStar's Improved Tooltips 3.2.1, CooldownTracker 1.0.0, MelonLoader 0.7.3 Open-Beta, Last Epoch 1.4.7.
“Shard” means a crafting material, not an equipment affix.

## Verdict and evidence boundary

**Two persistent-work defects are CONFIRMED-BY-CODE and survive in 3.1.0:** an active, repurposed cached TMP can force a full-scene scan every frame; a matched loot rule with no usable `requires` TMP can cause filter matching and two descendant enumerations every Update. These are the leading explanations for this report, not a confirmed attribution of the reporter's 17 FPS.

The shard-specific connection is **LIKELY**, conditional on runtime facts this source does not establish: which tooltip class crafting shards use, whether equipment TMPs remain active when reused, whether a pending item/rule exists, and whether `requires` is absent. No shard-only branch in this mod establishes those facts. A simpler tooltip can be worse precisely because expected equipment content never arrives, so retry gates never settle.

Read `CURRENT-WORK.md` first, including Tier B at line 9. Inspected current source and git history: repository HEAD `6860e65`, Tooltips release commit `601a9be` (3.1.0), predecessor `d419b64` (3.0.2). Tooltips source has no later committed delta and was clean before this document. Existing changes in sibling projects were left alone.
No reporter log, in-game capture, timing profile, or runtime object hierarchy was available. No build, deployment, commit, or source/config change was performed. Prior local review documents concern other sessions and are not the reporter's log.

Citation convention: `X.cs:line` means `medick_TerribleTooltips/src/X.cs:line` in the current tree. References below include method entry points and the decisive branches; lines 1–524 of `TooltipRecolor.cs` are unchanged between the two releases.

## Every frame-loop path

### Update: `TerribleTooltipsMod.cs:30–34`

1. **`GroundLabels.OnUpdate` (`GroundLabels.cs:41–67`).** Returns unless `LabelAltKey` is enabled and `s_altCache` is nonempty. Otherwise prunes dead/inactive ground labels, polls Alt, and returns if Alt did not change. On a transition it visits every cached label, calls `SetText` (save face color, assign text, restore color; `:197–202`), then native `sceneFollower.calculateDimensions` (`:62–63`). This is independent of crafting-shard hover and not gated by the tooltip master switch. Stable Alt means no text writes, but pruning still runs.
2. **`FilterRuleTooltip.MonitorUpdate` (`FilterRuleTooltip.cs:66–140`).** Master-off/rule-display-off returns; obtains `UITooltipItem.instance`; inactive tooltip clears pending state; null pending item or completed injection returns (`:70–89`). Otherwise enumerates descendant TMPs looking for a marked `requires` (`:97–108`), calls `TryGetMatchedRule` (`:110`, `:143–194`), formats a tag, and enumerates descendants again to write the first active `requires` (`:125–135`). Successful injection and no-match both latch completion. Missing target after a match does **not** latch completion.
3. **Filter subcalls.** `TryGetMatchedRule` obtains the filter/rules, calls native `filter.Match`, maps its result, then on unsuccessful resolution/exception manually walks enabled rules backwards with `Rule.Match(item, 0)` (`:149–191`). Name display additionally calls `GetRuleName`, possibly native `GetRuleDescription` (`:196–200`); default NumberOnly avoids that. `Dbg.Log` is debug-gated (`Prefs.cs:235–241`). Costs inside game/native matching are not quantified by this source.

### LateUpdate: `TerribleTooltipsMod.cs:36–40`

4. **Native range switch first** (`TooltipRecolor.OnLateUpdate`, `TooltipRecolor.cs:165–167` → `DriveNativeRangeSwitch`, `:132–162`). Reads the native flag every frame, restores it once on master-off, otherwise sets it only if it differs from `DeepRange` and calls `MarkDirty`. `DeepRange`/`DeepTier` read cached Alt plus pins (`:116–117`). Alt is polled later in this LateUpdate, so its switch response can occur on the next frame. Stable matching flag is cheap; an external writer can repeatedly invalidate it. Exceptions emit `[debug] native range switch failed: ...` each failure when debug is enabled.
5. **Master transition** (`TooltipRecolor.cs:169–177` → `RestoreVanillaOnMasterOff`, `:242–267`). Only on enabled→disabled: restores originals still carrying the marker, clears all three caches, and requests native relayout if the last tooltip is active. Debug line reports restored count.
6. **Alt transition** (`TooltipRecolor.cs:182–193`). Polls both Alt keys; on change sets cached state and `MarkDirty` (`:87–88`); while enabled calls `ReRenderFromOriginals` (`:269–299`). This prunes dead/inactive/markerless originals, composes remaining originals, assigns TMP text, then requests relayout if changed and active. Stable Alt avoids this whole recomposition branch.
7. **Catch-up scan** (`TooltipRecolor.cs:197–206`). While enabled and `s_lastTooltip.tooltipActive`, calls `ShouldScan` (`:94–114`) and conditionally `RunScan` (`:386–561`). Gate rejects a second scan in the same frame; accepts through `frameCount + 5` after dirtying, on a 0.5-second fallback, or if any active original has lost the four-ZWSP marker. Repeated MarkDirty can keep the window open indefinitely; the frame cap bounds frequency to one scan/frame, not scan cost.
8. **Range enforcement** (`TooltipRecolor.cs:208–234`). Enabled + not `DeepRange` + nonempty suppression cache allocates a removal list and visits every entry. Dead/inactive/repurposed entries are removed; rewritten single-line `Range:` text is replaced by the marker. Already-marked entries require no write. With `DeepRange` true this branch does not even prune. Independent of tooltip-active state.
9. **Tier-color enforcement** (`TooltipRecolor.cs:236–239`). While enabled and the cache is nonempty, removes dead/inactive TMPs and assigns every remaining TMP's cached color every LateUpdate. Active repurposed TMPs are not validated by content/owner here. Independent of tooltip-active state.
10. **`UnitBorder.OnLateUpdate` (3.1.0 only; `UnitBorder.cs:122–178`).** Gate requires master, border preference, and PlainText (`:983–990`). Gate-off invokes hide/cleanup (`:992–1018`); latched failure returns; zero owned borders returns. Otherwise visits remembered tooltips/rows, destroys dead objects, hides inactive or noncandidate rows, and refreshes only when the next-frame resync is due or `LayoutChanged` is true (`:164–169`, `:641–651`). The candidate requires marker suffix **and** `ttu` link (`:979–981`). No scene/descendant discovery happens in this LateUpdate itself. Hidden live rows remain cached and are revisited while borders are owned.

### Shared descendants and native callbacks that can add work in those frames

11. **`RunScan` full graph** (`TooltipRecolor.cs:386–561`): global `FindObjectsOfType<TextMeshProUGUI>` (`:392–393`) → `TrackFormatterHealth` (`:568–600`, another text/regex traversal until a hit) → `PruneOriginals` (`:602–610`, removes only dead/inactive) → parent-grade dictionary pass with up to two regex matches per nonempty TMP (`:406–418`) → composition pass over the same scene array (`:421–542`). Excludes composer/ground markers and object named `requires`; classifies by `Tier:`, `Range:`, or grade bracket, without tooltip ownership. Stores originals and writes composed text for multiline/unbracketed, range-only, or bracketed cases; standalone Tier widgets only enter the color cache. Any composed count requests relayout (`:546–547`). A scan finding zero eligible shard text still pays scene discovery and the passes.
12. **Composition leaves:** `HasBracket` runs two regexes (`TooltipRecolor.cs:322–323`); `Compose` splits lines, parses bracket/tier/range/sealed content and continuation text (`:616–729`); `ComposeUnbracketed` scans tiers and reconstructs lines (`:735–812`). Both call `ComposeCleanLine` (`:846–955`), which formats signals/colors/links via `JoinSignal` (`:958–966`), `Colors.TierColor` (`Colors.cs:31–41`), and optional validated `GreaterAffixHex` (`TooltipRecolor.cs:829–841`). `TierAnnotation` strips/parses details (`:816–824`). These allocate strings/lists/matches when composing, not on every unchanged row.
13. **Relayout and the second entry into scanning:** `RequestRelayout` calls native `UITooltipItem.UpdateLayout` with captured arguments under `s_relayouting` (`TooltipRecolor.cs:307–319`). The composer postfix skips its own relayout; ordinary game layout calls capture `s_lastTooltip/s_lastArgs` then run the same gate and scan (`:370–381`). The postfix does not itself require `tooltipActive`. LateUpdate does. Native layouts may recur every frame; exact shard call cadence is unobserved. The latch prevents recursive composer scans, not all native work or other postfixes.
14. **Dirty producers in native tooltip callbacks:** `SetAsItemTooltip`/`SetAsGroundTooltip` with nonnull data set pending filter item, reset injection, and mark dirty (`FilterRuleTooltip.cs:35–61`), with no same-item check. Formatter postfixes inject brackets and mark dirty on successful resolution (`AffixInjector.cs:67–98`, `:152–203`, `:218–234`). Affix lookup may iterate `item.affixes` and use `AffixList.GetAffix/HasProperty` (`:100–131`); injection formats grade/tier via `Colors` (`:48–61`, `Colors.cs:31–63`). Null/unresolved affix returns without dirtying. All three formatter `finally` blocks call `Trace`; when debug is on it normalizes/truncates the result and writes `[trace] ...` (`AffixInjector.cs:33–45`). Trace executes even if the master guard returned. These are native-event hooks, **not direct unconditional calls from OnUpdate**; shard use must be measured.
15. **Border graph from native UpdateLayout:** independent postfix calls `UnitBorder.Run` (`UnitBorder.cs:112–119`, `:180–262`) even on the composer's nested relayout. With gate enabled it enumerates this tooltip's active descendant TMPs (`:208`), checks marker/link, fingerprints and finds cached rows (`:944–948`, `:1097`), then `LayoutChanged`→`RefreshRow` or `SyncRow`. No once-per-frame gate here. New/text-changed rows refresh and schedule a next-frame resync; stable rows still sync on layout calls. Rows no longer seen are hidden. Placement logging occurs only for a changed candidate fingerprint (`:254–260`).
16. **Border expensive leaves:** `RefreshRow` forces the TMP mesh (`UnitBorder.cs:583–618`), allocates measured units, and calls `TryMeasure` (`:280–335`). That walks links, calls `TryMeasureRange`/`TryDividerCenter` (`:337–420`), or falls back to per-line prefix parsing (`:422–492`, `CountUnitBoxes/CountLinks :959–976`); tier parsing is a regex (`:951–956`). `EnsureSprite` lazily creates/caches 32×32 textures/sprites (`:773–823`); `CreateUnit` creates Image/LayoutElement siblings, plus the divider and lazy divider sprite (`:494–580`, `:825–848`). It does not recreate them each stable frame. `SyncRow` (`:621–638`) applies sprite/color (`:741–770`), sets active state, transforms/assigns geometry and sibling indices (`:667–738`), and logs canvas once/debug placement when requested (`:880–928`, reflection helper `:937–942`). Padding/thickness helpers clamp preferences (`:850–878`). Hide/destroy/cleanup helpers are `:1021–1075`; failure logs once, cleans up and latches off (`:1084–1095`).
17. **Other work is event-driven, not a hidden hover frame loop.** Ground-label setup starts a one-frame delayed coroutine (`GroundLabels.cs:70–146`), optionally calls public `CheckFilter` (`TerribleTooltipsApi.cs:18–44`), builds brackets (`GroundLabels.cs:149–190`) and assembles/writes labels (`:205–218`, `:197–202`). It requires a ground-label event, not opening crafting materials. Settings are built on Awake and callbacks save/dirty/re-render (`SettingsUi.cs:16–34`); `NativeSettings` builds controls; the Aaron's House coroutine requires its button (`SettingsUi.cs:159–160`, `AaronsHouse.cs:19–29`). Neither is called by the hover frame loops. No separate mod OnGUI/fixed-update loop was found.

## Ranked candidates, cheap cases, and falsifiable checks

Rank refers to explanatory fit for this report, not measured CPU share. Multiple mechanisms can coexist. Use frame time as well as displayed FPS; repeat one variable at a time. Each suggested hover experiment is about 30 seconds after setup; none was executed for this diagnosis.

### 1. Active pooled TMP loses its marker and becomes permanently noncomposable

**CONFIRMED-BY-CODE conditional defect; LIKELY report mechanism.** Equipment tooltip populates `s_originals` → game reuses an active TMP for empty/plain crafting text → `ShouldScan` sees missing marker (`TooltipRecolor.cs:103–109`) → scene scan → pruning retains the active TMP (`:602–610`) → composition skips empty/noncandidate text (`:425–456`) without removing its original → same condition next frame. Even a standalone Tier replacement can leave the old original without a new marker (`:477–491`). No repeated formatter call, logging or relayout is needed to sustain this loop.

**Why shards can be worse:** equipment text that is eligible for composition gets its marker restored, allowing the gate to settle; a shard description with no tier/range/bracket never does. The large material panel can also increase the number of active TMPs traversed. Neither reuse nor panel TMP count has been observed. If the shard has an entirely separate tooltip and previous widgets become inactive, this explanation loses its prerequisite.
**Cheap:** no cached originals; repurposed widget becomes inactive/destroyed; replacement gets composed/marked; or cache was cleared. With no other invalidation, scanning falls back to about 2/s after the dirty window.
**30-second check:** set rule display Off to isolate candidate 2. Compare shard-first after a fresh master off→on with equipment→shard without a hover gap; hold each still >5 seconds. Repeat the master reset after reproducing. History-dependent onset and recovery after cache clear support this path. Closing hover alone need not clear originals: pruning runs during scans. No dependence weakens it but does not rule out an unrelated active cached widget.
**Decisive trace:** for each scan record trigger, frame, TMP instance/path, active flag, marker presence, eligibility and cache removal. An unchanged active markerless, ineligible TMP remaining cached across successive scans proves the loop. Stable 0.5-second scanning falsifies an every-frame-loop attribution in that interval. **Existing DebugLog has no scan-trigger/cache trace; no grep can directly prove this.**

### 2. Filter-rule injection retries forever when the shard has no active `requires`

**CONFIRMED-BY-CODE conditional defect; LIKELY report mechanism.** Pending item + active singleton + rule enabled + matched rule + no active usable target causes both `GetComponentsInChildren` passes and matching every Update (`FilterRuleTooltip.cs:89–137`). `s_injected` is set only on preexisting marker, no-match, or successful write. Stale pending data can also survive a switch that does not call SetAs hooks and does not let MonitorUpdate observe an inactive tooltip (`:38–61`, `:82–89`).
**Why shards can be worse:** an equipment tooltip normally offers the requirements destination, so this is one-shot. A crafting-material layout may omit that field; this is a runtime hypothesis, not an inspected game-layout fact. Large/complex loot filters amplify each retry, including manual fallback matching. If shards never set pending data and no stale item survives, or no rule matches, the loop cannot occur.
**Cheap:** rule display Off, master Off, no pending item/filter/match, successful target injection, or persisted target marker. A no-match returns completion even though its first matching attempt may be costly.
**30-second check:** reproduce a static shard hover with rule display NumberOnly, then Off, then NumberOnly, keeping the same filter/item sequence. Re-enter and wait >1 second after each settings change (settings also dirty the composer). Sustained relief only when rule display is Off strongly isolates this lane. After reproducing, compare with the filter deselected; history-sensitive equipment→shard behavior tests stale pending data.
**Log grep:** `\[debug\] (rule #[0-9]+ injected|marker already in 'requires')`. A successful line shows completion at that instant, but repeated SetAs calls can reset it. No line does **not** establish retries: target failure is silent, as are many exceptions. Decisive trace: per-item/generation attempt count, matchingRuleNum, active `requires` count, and `s_injected`; matching every frame with zero targets confirms it.

### 3. Real repeated content rewrites or dirty signals keep expensive scans alive

**NOT PROVEN for shards; enabling paths CONFIRMED-BY-CODE.** Frequent SetAs calls reset the five-frame window (`FilterRuleTooltip.cs:43,59`); successful formatter injections do too (`AffixInjector.cs:90,199,230`). Game/other-mod rewrites of composable text can remove the marker anew each frame. A competing writer to the native range flag can dirty every frame (`TooltipRecolor.cs:154–158`). Recomposition then writes TMPs and requests another native layout, increasing cost; the recursion latch only bounds our composer re-entry.
**Why shards could be worse:** a shard-specific game/mod tooltip refresh path could call setters/formatters much more often, or show text containing `Tier:`/`Range:` that the global classifier repeatedly transforms. No evidence here establishes such a game path, particular shard text, or Fallen culpability. Null/unresolved `AffixFormatter` alone does **not** MarkDirty; it still traces.
**Cheap:** content generated once, native range flag agrees, marker remains present; dirty window expires. Scans may still occur via candidate 1 or fallback.
**Log grep:** `\[trace\] (AffixFormatter|UniqueBasicModFormatter|ImplicitFormatter)` and `\[debug\] native range switch failed:`. Dense repeated identical results while stationary support repeated formatter activity; they do not prove it wrote a bracket or dirtied. No formatter flood cannot exclude SetAs, direct TMP writes, or successful native-flag contention, which have no dedicated log.
**30-second check:** hold one shard still for 10s, sweep between shards for 10s, then hold equipment for 10s; compare trace cadence and frame time. Later repeat a prepared run with Fallen absent and the same TT settings. Relief isolates an interaction, not which mod is wrong. A trace with stable range flag, no new dirty events and no repeated eligible-text overwrites falsifies this candidate and separates it from candidate 1.

### 4. Ordinary scene-wide fallback scanning is already costly in the materials UI

**CONFIRMED-BY-CODE recurring cost; NOT PROVEN sufficient for 17 FPS.** Even with no eligible affixes, an active remembered tooltip triggers fallback every 0.5 seconds (`TooltipRecolor.cs:99–100,199–203`). Scene discovery plus health/grade/composition passes scale with all active text, not shard complexity (`:392–456`). A material panel with many visible names/counts could therefore cost more than an equipment-only panel. Counts and milliseconds are unknown; this also amplifies candidates 1 and 3.
**Cheap:** fewer active TMPs; no active remembered tooltip/layout calls; or master disabled. No brackets is not an early exit before scene enumeration. A single opening can also incur scans across the dirty frame window.
**30-second check:** rule display Off, debug Off; hold a stationary shard after settling and watch whether spikes recur near 0.5s rather than every frame. Compare a material panel showing fewer rows using an existing search/filter, if available. A timing trace showing RunScan not correlated with spikes falsifies this attribution; every-frame scan frequency instead requires another gate trigger.
**Log grep:** `no affix brackets seen in 20 tooltip scans`. This is a once-per-session health warning, **not evidence that a shard should have brackets**. Its absence is inconclusive (a different scene TMP can satisfy health, or the warning already fired). It cannot measure scan cadence without a known/reset counter; there is no existing per-scan timing line.

### 5. Debug logging / repeated caught errors magnify a hot path

**NOT PROVEN as the original trigger.** Reporter says the attached log used debug; that does not establish debug was enabled when stutter began. Formatter traces are unthrottled (`AffixInjector.cs:33–45,93–97,202,233`) and run even after master-off returns. Repeated errors also log when debug is enabled (`TooltipRecolor.cs:161,559`, `AffixInjector.cs:92`). The health warning and first recolor warning are latched and cannot themselves sustain a flood.
**Why shards could be worse:** only if their native formatters/errors recur more often; a small result string is not inherently expensive. Trace-only null/unresolved formatter calls could produce I/O without dirtying. **Cheap:** debug Off, low call rate, no repeated errors.
**Log grep:** `\[trace\]|\[debug\] (multi-stat affix lookup failed:|native range switch failed:|tooltip clean-line error:)|tooltip clean-line failing`. Count lines/second around the hover, not total file size. One-time `AffixFormatter: item=null` or `multi-stat affix: no match` is not a flood.
**30-second check:** in prepared runs with identical hover order and UI, compare DebugLog on/off. If performance is unchanged, logging is unlikely dominant. Master-off alone is an imperfect control because formatter Trace still runs. Separate native exceptions in Fallen/CooldownTracker require their own stack/timestamp correlation; no such log was inspected.

### 6. UnitBorder adds a 3.1.0 cost or amplifies relayout churn

**CONFIRMED-BY-CODE added work; NOT PROVEN material shard regression; excluded as the cause of a genuine 3.0.2 report.** It did not exist in `d419b64`. Its LateUpdate is cache-only: no borders returns; noncandidate shard rows hide and skip mesh generation; stable candidate geometry does not refresh. Equipment with border candidates normally has more border work than an unmarked shard, so this is not an unconditional shard penalty.
The **UpdateLayout postfix**, however, performs a descendant scan every call, including nested relayouts, with no frame/content gate (`UnitBorder.cs:112–119,208`). Repeated candidate rewrites/layout changes can invoke ForceMeshUpdate (`:586`) and geometry synchronization. LateUpdate also refreshes on pending resync/size/line/padding changes, and retained hidden rows add traversal overhead. Thus it can worsen an existing layout storm, particularly with visible comparison/equipment candidates, but candidate 1's zero-composition scans do not automatically request extra layouts.
**Cheap:** UnitBorder Off, non-PlainText style, no owned borders/candidates, stable layout. BorderDebug defaults false; when true placement logs/reflection can recur (`Prefs.cs:170`, `UnitBorder.cs:904–927`).
**30-second check (3.1.0):** keep PlainText and all other settings fixed; repeat shard and equipment hover with UnitBorder on/off. Wait out setting invalidation. If only equipment improves, borders do not explain shard specificity. If shard improves, trace native UpdateLayout frequency, border candidates, and RefreshRow counts before blaming LateUpdate.
**Log grep:** `\[UnitBorder\] (placed|dbg row=|OFF|off)`; `placed` is fingerprint-gated, not a per-layout/mesh counter, and silence does not mean Run was skipped. No UnitBorder lines should originate from this mod's 3.0.2 DLL; verify the startup version if they appear.

## Minimal corrective outline — proposal only

Use the existing **Tier B shape** in `CURRENT-WORK.md:9`: “scope the scene scan to tooltip descendants + non-substring markers” and “s_suppressedRanges prune outside DeepRange.” This directly addresses scene cost/ownership and adjacent cache retention. Scoping alone does **not** terminate candidate 1 inside the tooltip, and marker replacement alone does not repair candidate 2. Add explicit stale-original retirement and bounded missing-target handling; no composer/settings rebuild is needed.

The queued marker concern is concrete: composer uses four ZWSPs (`TooltipRecolor.cs:51`), ground labels three (`GroundLabels.cs:27`), filter tags two (`FilterRuleTooltip.cs:28`), and ownership checks use Contains. Longer markers contain shorter ones. This can confuse ownership/health checks but is not, by itself, proof of a shard performance loop. The unrelated Tier B continuation-tint and ground-label-style cache work stays outside this corrective outline.
